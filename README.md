### Задача 1: API Gateway

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:
- маршрутизация запросов к нужному сервису на основе конфигурации,
- возможность проверки аутентификационной информации в запросах,
- обеспечение терминации HTTPS.

Обоснуйте свой выбор.

| Критерий | Nginx | Kong Gateway | Traefik Proxy | Envoy Proxy |
|---|---|---|---|---|
| Маршрутизация по конфигурации | Да: `location`, `upstream`, переписывание URI | Да: Services/Routes, декларативная конфигурация и Admin API | Да: routers/services/middlewares, динамическая конфигурация | Да: маршрутизация L4/L7 через конфигурацию xDS/статический файл |
| Проверка аутентификации | `auth_request` к внешнему сервису; возможна интеграция с OAuth/OIDC через внешний компонент | Большой набор плагинов: Key Auth, Basic Auth, OAuth/OIDC в зависимости от плагина/редакции | `ForwardAuth`, BasicAuth, JWT/OIDC через middleware/plugin или внешний сервис | Фильтры ext_authz, JWT и интеграции с внешними системами |
| TLS termination | Да, `listen ... ssl`, сертификат и ключ | Да, сертификаты и TLS на маршрутах | Да, сертификаты вручную или автоматизация ACME/Let's Encrypt | Да, TLS-контексты и сертификаты в listener/filter chain |
| Балансировка | Да: round-robin, least connections, hash; часть возможностей зависит от сборки/версии | Да, балансировка между upstream targets | Да, балансировка сервисов и health checks | Да, развитые алгоритмы и health checking |
| Эксплуатационная сложность | Низкая для небольшого числа маршрутов; конфигурация текстовая | Средняя/высокая: больше возможностей, сущностей и компонентов управления | Низкая/средняя; удобно для контейнеров и динамического discovery | Высокая: много возможностей и параметров, требует опыта L7 proxy |
| Когда выбирать | Простой, понятный шлюз для небольших и средних систем | API platform, много команд, централизованные политики, плагины и API management | Контейнерная среда с часто меняющимися сервисами | Сложный service mesh, gRPC и требовательные L7-сценарии |

Для данного случая выбираю Nginx. Он удовлетворяет всем заданным требованиям: маршрутизирует URL на основе конфигурации, проверяет токен через `auth_request` и может завершать HTTPS на входном соединении. `auth_request` выполняет внутренний подзапрос и пропускает основной запрос только при ответе авторизации 2xx; ответ 401/403 отклоняет доступ.

### Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:

- поддержка кластеризации для обеспечения надёжности,
- хранение сообщений на диске в процессе доставки,
- высокая скорость работы,
- поддержка различных форматов сообщений,
- разделение прав доступа к различным потокам сообщений,
- простота эксплуатации.

Обоснуйте свой выбор.

| Критерий | RabbitMQ | Kafka | NATS JetStream | Redis Streams |
|---|---|---|---|---|
| Кластеризация/надёжность | Кластер; quorum queues/streams реплицируют данные и переживают отказ узла при наличии кворума | Репликация разделов по брокерам; высокая отказоустойчивость при корректном replication factor и ISR | Репликация stream по узлам; кластерный режим | Репликация Redis зависит от конфигурации; Streams хранятся в данных Redis, HA требует Redis Sentinel/Cluster и аккуратной настройки |
| Диск/повторное чтение | Durable queues + persistent messages; поведение зависит от типа очереди и настроек | Основной сценарий: журнал на диске, retention и replay по offset | JetStream хранит stream в памяти/файлах в зависимости от storage policy; поддерживает replay | AOF/RDB persistence; consumer groups, pending entries и replay доступны, но модель хранения Redis отличается от специализированного брокера |
| Производительность | Высокая для обычной очередной доставки и маршрутизации | Очень высокая пропускная способность при потоковой обработке больших объёмов | Очень низкие задержки и высокая производительность при относительно простой архитектуре | Высокая производительность для простых потоков и сценариев рядом с Redis |
| Форматы сообщений | Байты; формат определяет приложение (JSON, Protobuf, Avro и т. п.) | Байты; формат определяет приложение, доступна интеграция со Schema Registry | Payload — байты; формат определяет приложение | Поля Stream entries; формат значений определяет приложение |
| Права на потоки/очереди | Пользователи, vhost permissions и granular resource/topic permissions | ACL для операций и ресурсов, включая топики | Subject-based permissions и permissions для accounts/users | ACL-команды ограничивают доступ к командам и ключам; изоляция отдельных потоков зависит от именования/ACL-политик |
| Сложность эксплуатации | Низкая/средняя для одиночного узла; кластер и quorum queues требуют понимания кворума | Высокая: брокеры, partitions, replication, retention, consumer lag и координация кластера | Низкая/средняя для базового запуска; JetStream/кластер требует продуманной конфигурации | Низкая, если Redis уже используется; надёжность и семантику очередей нужно проверять под нагрузкой |
| Сильная сторона | Гибкая маршрутизация сообщений, подтверждения, DLQ и привычная модель очередей | Долговечный event log, replay и очень большие потоки событий | Простая архитектура, low latency, subjects и JetStream persistence | Простота и близость к уже существующему Redis |

Для общей микросервисной системы я выбрал бы RabbitMQ там, где требуется устойчивость к отказу узла. Он хорошо сочетает маршрутизацию, подтверждения доставки, повторные попытки/dead-letter очереди, контроль доступа и приемлемую операционную сложность. Тело сообщения не привязано к конкретному формату — JSON, Protobuf и другие схемы выбирает приложение. В данном случае RabbitMQ — сбалансированный вариант по совокупности требований.
